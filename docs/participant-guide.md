# AI와 만드는 우리 동네 지도

각자 자신이 사는 동네에서 가로 1km × 세로 1km 구역을 고르고, AI가 작성한 수집 코드를 실행해 그 구역의 OSM·Overture 데이터를 받습니다. 수집한 지도를 입체로 그리고 화풍을 입힌 뒤 브라우저에서 이동·확대하는 지도로 완성합니다.

이 실습에서는 공유받은 저장소에서 **AI와 코드를 만들고 직접 실행합니다.** 지도 제작 완성 코드는 제공하지 않습니다. 기본 목표는 로컬에서 이동·확대할 수 있는 낮 지도입니다. 야경·실제 지형·인터넷 공개는 선택 과제입니다.

## 이번 핸즈온에서 만들 것

각자 사는 동네의 지도 데이터를 입체 그림으로 바꾸고, 브라우저에서 이동·확대할 수 있는 지도로 만듭니다. 처음부터 모든 선택을 할 필요는 없습니다. 동네 중심은 OSM을 살펴보는 1단계에서 정하고, 화풍은 이미지를 편집하는 4단계에서 정합니다.

1. **환경 준비:** 저장소 안에 도구를 설치하고 이미지 편집 모델을 미리 받습니다.
2. **동네 데이터 수집:** OpenStreetMap에서 동네 중심을 고르고, 그 1km × 1km 범위의 OSM·Overture 자료를 모읍니다.
3. **지도 만들기:** 데이터를 정리해 bin으로 굽고, three.js로 그려 타일 이미지를 촬영합니다.
4. **그림으로 바꾸기:** 이때 원하는 화풍을 정하고, 맥에서 MFLUX로 이미지를 편집합니다.
5. **웹 지도 완성:** 결과 타일을 확인·합성해 브라우저 지도에 올립니다.

## 시작 전에 읽기

### 진행 순서와 역할

**장소·화풍 선택 → AI에게 코드 요청 → 명령 실행 → 결과 확인** 순서로 진행합니다.

| 참가자가 할 일 | AI에게 맡길 일 |
| --- | --- |
| 동네 좌표·화풍 선택 | 범위 계산, 데이터 수집·가공 코드 작성 |
| 설치·수집·촬영·편집 명령 실행 | 엔진·촬영·이미지 처리·뷰어 구현 |
| 원본과 결과를 보고 다음 단계 판단 | 오류 원인 분석과 코드 수정 |
| 로그인·공개 배포·환경 삭제 | 필요한 설정·명령과 주의할 점 안내 |

OSM 화면에서는 **동네 중심 좌표만 고르면 됩니다.** 건물·도로 추출은 AI가 작성한 코드가 수행합니다. 실행 기능이 있는 코딩 AI에는 명령 실행도 맡길 수 있습니다. 장소와 화풍이 맞는지 확인하는 일은 참가자가 합니다.

**AI 요청문은 코딩 AI에 복사해 보낼 작업 지시입니다.** 요청문 앞의 설명에서 무엇을 만들지 확인하고, 대괄호가 있으면 내 좌표·화풍·관찰 결과로 바꾸세요. AI가 실제 파일과 코드를 작성한 뒤 실행합니다.

**‘실행’ 블록은 바로 위 요청문으로 코드를 만든 뒤 사용하세요.** 설치·모델 준비 명령을 제외한 실습 명령은 처음부터 저장소에 들어 있지 않습니다. 터미널 환경을 준비하는 방법은 아래 0단계에서 설명합니다.

## 준비물 확인

모델 파일은 약 15GB입니다. 셋업 도구와 모델을 받을 저장 공간을 확보하세요. 로컬 이미지 편집 속도와 메모리 여유는 4단계에서 실제로 시험합니다. 기기 정보를 AI에 미리 입력하거나 별도 파일에 기록할 필요는 없습니다.

| 준비물              | 확인할 내용                                                                                                       |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Apple Silicon 맥북  | 이 셋업 스크립트의 대상 환경. MFLUX는 8GB에서 권장하지 않으며, 16GB는 소규모 시험부터 가능                              |
| 메모리·저장 공간    | 24~32GB 메모리와 여유 공간 30GB 이상을 계획용으로 권장. 공식 최소 사양이나 성공 보장은 아님                    |
| 인터넷              | 지도 자료·패키지·최초 모델 다운로드에 사용. 기본 4B 모델 다운로드는 약 15GB                                       |
| 코드 편집기·코딩 AI | 공유 저장소의 파일을 열고, 단계별 요청문으로 코드를 만들 수 있는 도구                                                  |
| Python·uv           | 셋업 스크립트가 기존 Python 3.12를 재사용하거나 저장소 안에 준비                                                  |
| Node.js·pnpm        | 기존 arm64 Node.js 20.19~26·pnpm 10.x 설치 여부 확인 후 재사용                                                 |
| Chromium            | 셋업 스크립트가 Playwright 호환 브라우저를 저장소 캐시에 준비                                                     |

설치 스크립트가 지원 환경을 확인하고 필요한 도구를 준비합니다. 별도로 버전 정보를 모아 AI에게 보낼 필요는 없습니다.

## 0. 공유 저장소 셋업하고 같은 폴더에서 시작하기

**목표:** 이 저장소에서 실습 코드를 실행할 도구와 이미지 편집 모델을 준비합니다.

**결과물:** 실습 실행 환경, 다운로드한 이미지 모델, AI가 이어서 참고할 `progress.md`

### 참가자가 할 일

1. 진행자가 공유한 저장소를 clone하거나 **Code → Download ZIP**으로 받아 압축을 푸세요.
2. 그 폴더를 편집기와 터미널에서 여세요. README와 `scripts/setup.sh`가 보이는 위치여야 합니다.
3. 먼저 기본 도구를 설치하고, 이어지는 AI 요청 두 개를 순서대로 진행하세요. 첫 요청은 작업 환경과 기록 파일을 준비하고, 다음 요청은 뒤에서 사용할 이미지 편집 모델을 준비합니다.

먼저 필요한 도구와 패키지를 설치합니다. Node.js·pnpm은 설치 여부와 호환 버전을 확인해 기존 것을 사용합니다. 없는 도구와 MFLUX·모델·캐시는 삭제하기 쉽도록 기본적으로 이 프로젝트 안에 설치합니다.

```bash
bash scripts/setup.sh
```

`setup.sh`는 설치가 끝나면 자체 검사를 실행합니다. 성공 메시지가 나오면 기본 도구 설치와 검사가 끝난 것입니다. 이후 Codex CLI나 Codex Desktop의 명령마다 저장소 환경을 적용할 수 있도록 AI에게 작은 실행 도우미를 만들게 합니다.

기존 Node.js는 arm64 20.19 이상~26 계열, pnpm은 10.x를 사용합니다. pnpm 10.32.1처럼 세부 버전이 달라도 허용합니다. 호환 도구가 없으면 저장소 안에 대체 버전을 준비합니다.

### 무엇이 어디에 설치되나요?

| 항목 | 준비 방식·위치 | 실습 환경 삭제 시 |
| --- | --- | --- |
| 기존 Python·Node.js | 호환 버전이면 그대로 사용 | 보존 |
| 추가 Python·Node.js | 필요한 경우에만 `.tools`에 설치 | 삭제 |
| uv·pnpm | 호환 도구 재사용, 없으면 `.tools`에 설치 | 저장소에 추가한 도구만 삭제 |
| MFLUX·Python 패키지 | 저장소 전용 `.venv` | 삭제 |
| three.js·Playwright | `node_modules` | 삭제 |
| 모델 가중치·Chromium·도구별 캐시 | `.cache` | 삭제 |
| 직접 만든 코드·지도 원본·촬영/변환 이미지·완성 지도 | 소스와 `data/`, `captures/`, `stylized/`, `corrected/`, `output/` 등 | 보존 |

설치 환경은 마지막 단계의 삭제 명령으로 정리합니다. 기존 전역 도구와 실습 결과는 남습니다. 자세한 설치·복구 방법은 저장소의 `docs/setup.md`를 참고하세요.

### AI 요청문 — 실행 도우미와 프로젝트 맥락 만들기

Codex CLI는 명령마다 별도 셸에서 실행할 수 있어 터미널 환경 설정이 이어지지 않을 수 있습니다. 아래 요청은 매 명령에 프로젝트 환경을 적용하는 `scripts/run.sh`와, 새 대화에서 목표와 진행 단계를 이어갈 `progress.md`를 준비합니다. 이 요청에서는 도구를 다시 설치하거나 모델을 다운로드하지 않습니다.

```text
README.md, AGENTS.md, docs/participant-guide.md를 읽고 저장소 규칙과 실습 목표를 파악해.
Codex CLI와 터미널에서 매 명령에 프로젝트 환경을 적용하도록 scripts/run.sh를 만들어.
스크립트는 bash로 실행하고, 저장소 경로를 찾아 그 위치로 이동해.
.tools/activate를 스크립트 안에서 불러온 뒤 전달받은 명령을 exec로 실행해.
인자가 없거나 환경 파일이 없으면 해결 방법을 출력하고 종료해.
전역 환경은 바꾸지 마. 이후 모든 실습 명령은 bash scripts/run.sh <명령과 인자>로 실행해.

README와 가이드를 기준으로 프로젝트 목표, AI와 참가자의 역할, 현재 상태와 다음 단계를
짧게 progress.md에 정리해. 새 AI 대화는 이 파일과 가이드의 현재 단계를 읽고,
단계가 끝나면 실제로 확인한 결과만 갱신하게 적어. 참가자에게 별도 정보를 묻지 마.

progress.md에는 기본 도구 설치가 끝났고 다음 단계에서 이미지 편집 모델을 준비한다고 기록해.
지도 코드는 아직 작성하지 마.
```

### AI 요청문 — 이미지 편집 모델 준비

이 모델은 뒤의 4단계에서 촬영한 지도 이미지를 원하는 화풍으로 편집할 때 MFLUX가 사용하는 이미지 생성 모델입니다. 약 15GB의 모델 파일을 이 저장소에 받아 두며, 이 단계에서는 이미지를 편집하지 않습니다. 준비된 모델이 있으면 재사용하고, 없을 때만 다운로드합니다.

```text
README.md, AGENTS.md, docs/participant-guide.md, progress.md를 읽고 현재 단계를 확인해.
이 단계는 4단계의 지도 이미지 편집에 사용할 FLUX.2 klein 4B 모델을 준비하는 작업이야.
모델을 학습하거나 이미지를 편집하지 말고, 저장소 안에 모델 파일만 준비해.

먼저 setup/model.json의 저장소와 리비전을 확인해.
실행 전에 참가자에게 이 모델이 4단계 이미지 편집에 쓰이고 약 15GB를 다운로드하며,
이 단계에서는 이미지를 편집하지 않는다고 설명해.
reports/model.json이 같은 저장소·리비전을 가리키고,
.cache/model이 보고서의 실제 모델 폴더를 가리키며 그 폴더가 있으면 이미 준비된 거야.
이미 준비되어 있으면 다운로드를 건너뛰어.

bash scripts/run.sh pnpm run setup:model을 실행해.
다운로드 실패 시 원인과 해결 방법을 기록하고 성공으로 표시하지 마.

확인한 모델 준비 상태와 다음 단계만 progress.md에 반영해.
```

## 1. 동네 범위를 정하고 데이터를 수집하기

**목표:** 내 동네의 1km 사각형을 확정하고, 같은 구역의 OSM·Overture 원본을 확보해 위치를 비교합니다.

**결과물:** 구역 설정, 출처별 원본 데이터, 범위·수집 결과 미리보기

### 참가자가 할 일

1. [OpenStreetMap](https://www.openstreetmap.org/)에서 만들고 싶은 동네를 찾으세요.
2. 중심점을 우클릭해 ‘주소 보기 / Show address’ 등으로 위도·경도를 확인하세요. 메뉴가 다르면 지도 중심을 맞춘 뒤 URL의 `#map=확대율/위도/경도`에서 읽을 수 있습니다.
3. 위도와 경도를 구분해 아래 요청문에 넣으세요. 기본 지형은 평면으로 시작합니다.

### 1-1. 범위 미리보기

**목표:** 데이터를 받기 전에 중심점과 1km 사각형이 원하는 곳인지 확인합니다.

**AI 요청문 설명:** AI가 중심 좌표를 설정 파일로 저장하고, 선택한 1km 사각형을 보여주는 코드를 작성·실행합니다.

```text
동네 이름은 [동네 이름], 중심 위도는 [위도], 경도는 [경도]야.
이 중심의 가로 1000m × 세로 1000m 범위를 만들어줘. 반경 1km가 아니야.
미터 좌표계에서 중심으로부터 동서남북 각각 500m로 계산해.
위경도에 임의의 고정 도 단위를 더하지 말고 미터 좌표계에서 계산해.
config/workshop.json에 동네 이름·중심 위도/경도·미터 좌표계·원점·범위·지형=평면을 저장해.

중심점과 사각형을 볼 수 있는 미리보기 코드를 작성하고 실행해.
reports/area.html에 배경 지도·중심점·사각형 경계와 가로/세로 길이를 표시해.
로컬 데이터는 HTML에 포함해. 파일 직접 열기(file://) 대신,
reports/만 제공하는 로컬 HTTP 서버를 127.0.0.1에서 실행하고 접속 URL을 알려줘.
OSM 배경 타일은 출처를 표시하고 Referer 전송을 막는 설정을 사용하지 마.
배경 지도에는 인터넷 연결이 필요함을 알려줘.

오류가 나면 원인을 확인해 수정하고, 생성된 파일과 범위가 1000m × 1000m인지 확인해.
서버 실행·종료 방법과 접속 URL, 파일 경로·확인한 결과를 progress.md에 기록해.
다음 수집에서도 같은 설정과 코드를 이어 쓸 수 있게 해. 이번에는 범위 미리보기까지만 만들어.
```

AI가 안내한 `http://127.0.0.1:포트/area.html` 주소로 접속해 배경 지도와 내가 고른 동네의 1km 사각형을 확인하세요. 파일을 직접 열면 OSM 배경 타일이 차단될 수 있습니다. 범위가 틀리면 좌표부터 수정합니다.

### 1-2. OSM 수집

**목표:** 확정한 구역의 건물·도로·물·공원을 OSM에서 받아 지도에 표시합니다.

이 실습은 OSM 데이터를 조회하는 [Overpass API의 공용 서버](https://wiki.openstreetmap.org/wiki/Overpass_API#Public_Overpass_API_instances)를 사용합니다. 가입·API 키 발급이 필요 없는 서버를 선택하므로 인터넷 연결만 있으면 시작할 수 있습니다. 공용 서버는 혼잡하거나 요청을 제한할 수 있어, 받은 원본은 저장해 재사용합니다.

## 2. 데이터를 정리하고 bin 만들기

**목표:** 지도 자료를 정리하고 장면 생성에 필요한 준비 계산을 오프라인에서 끝내, 브라우저가 바로 사용할 렌더링 데이터와 메타데이터를 bin에 저장합니다(bake).

**결과물:** `data/processed/neighborhood.bin`, 파일 구조 설명, Python·JavaScript 로더와 읽기 확인 결과

**무엇을 미리 계산하나요?** 입력 데이터와 설정만으로 결정되는 좌표 변환·중복 제거·높이 결정·형상 생성·재질별 구간·건물 조회 정보·경계 상자를 미리 계산합니다. 정점·인덱스는 그 결과의 일부입니다. bin은 이 결과들을 담는 프로젝트 전용 형식이며, 브라우저가 준비 계산을 반복하지 않도록 저장 코드와 로더를 함께 만듭니다. 브라우저는 데이터를 읽어 GPU에 올리고 카메라·조명·사용자 조작에 맞춰 화면을 그립니다.

bin의 형상은 미터 단위의 3D 좌표로 저장합니다. 촬영 해상도·카메라 방향·축척·겹침은 3단계의 설정이므로, 이것만 바꿀 때는 bin을 다시 만들 필요가 없습니다.

```text

```

## 3. 도시를 그리고 PNG로 촬영하기

**목표:** bin으로 동네의 입체 지도를 띄우고 카메라를 확정한 뒤, 화풍 변환을 시험할 이웃 PNG 3장을 촬영합니다.

**결과물:** three.js 화면, 전체 촬영 위치 목록, 시험 PNG 3장과 대표 이미지 `captures/pilot.png`

### 참가자가 할 일

아래 요청문을 순서대로 하나씩 전달합니다. AI가 코드를 작성·실행하면 결과를 확인하고 다음 요청으로 넘어갑니다. 참가자는 지도 확인과 카메라 방향 선택, 촬영 결과 확인을 맡습니다.

| 설정             | 값                               |
| ---------------- | -------------------------------- |
| 카메라           | 방향·축척을 고정한 정사영 카메라 |
| 출력             | 768×768px PNG, DPR 1             |
| 축척             | 카메라 화면 평면 기준 0.4m/px    |
| 이동 간격 / 겹침 | 576px / 192px                    |

한 장이 담는 화면 평면의 범위는 307.2m × 307.2m입니다. 해상도를 낮추면서 축척도 조정해 기존 1024px·0.3m/px 촬영과 같은 범위와 장수를 유지합니다.

정면으로 내려다보는 1km 사각형은 이 설정에서 5×5장으로 덮을 수 있습니다. 비스듬한 시점에서는 장수가 달라지므로 AI가 실제 투영 범위로 계산해야 합니다. 25장을 고정값으로 쓰지 않습니다.

이미 다른 해상도로 촬영했다면 기존 결과를 별도로 보관하고, 3-2부터 새 설정으로 촬영 위치 목록과 이미지를 다시 준비하세요.

### 3-1. 입체 지도 띄우기

**목표:** 2단계의 bin으로 동네의 건물·도로·물·공원을 표시합니다.

**AI 요청문 설명:** 저장된 형상을 three.js에 연결하고 서버를 실행합니다. 촬영 코드는 다음에 작성합니다.

```text

법선 계산·재질 구간 구성·경계 상자 계산을 런타임에서 반복하지 마.

pnpm run dev로 localhost:5173 서버와 web 화면이 열리게 해.
프레임워크는 필요하지 않아. 서버는 실습에 필요한 정적 파일만 제공해.
```

### 3-2. 카메라 방향과 좌표 맞추기

**목표:** 원하는 시점을 확정하고 엔진과 Python이 같은 위치를 계산하도록 맞춥니다.

여기서 **카메라 방향**은 동네를 어느 쪽에서, 얼마나 기울여 내려다볼지를 뜻합니다. 건물의 옆면까지 보이는 입체 그림으로 만들지, 일반 지도처럼 위에서 볼지를 정하는 것입니다.

- **기본: 남쪽 위에서 45도로 내려다보기** — 건물의 지붕과 옆면이 함께 보입니다. 아래 요청문을 그대로 사용하세요.
- **수직으로 내려다보기** — 일반 지도처럼 지붕과 도로 배치가 잘 보입니다. 아래 요청문의 첫 두 줄을 “동네 중심의 바로 위에서 수직으로 내려다봐. 화면 위쪽은 북쪽, 오른쪽은 동쪽으로 맞춰.”로 바꾸세요.

45도는 시선과 수평 지면 사이의 각도이며, 수직으로 내려다보면 90도입니다. 카메라 좌표를 직접 계산할 필요는 없습니다. AI가 설정한 화면을 보고 “조금 더 위에서 내려다보게 해줘”처럼 조정해도 됩니다. 방향을 바꿨다면 AI에게 좌표 검증까지 다시 요청한 뒤 다음으로 넘어가세요.

**AI 요청문 설명:** 선택한 시점을 적용하고, 촬영과 이후 이미지 합성에서 같은 좌표를 사용하도록 카메라 설정과 변환식을 저장·검증합니다.

```text
동네 남쪽 위에서 중심을 향해, 수평 지면 기준 45도로 내려다보게 해.

768×768, DPR 1, 카메라 화면 평면 기준 0.4m/px로 촬영하도록 설정해.
config/workshop.json에 정사영 카메라 방향·축척과 세계 좌표→전역 픽셀 변환을 저장해.
이후 촬영과 이미지 합성은 이 설정을 함께 사용하고 촬영 중 방향·축척은 바꾸지 마.
높이가 다른 기준점 몇 개를 엔진과 Python에서 투영해 수치로 비교해.
오차 기준과 비교 결과를 reports/capture.md에 기록하고, 맞지 않으면 수정해.
카메라를 적용한 화면 주소와 확인 결과를 알려주고 progress.md를 갱신해.
촬영 코드는 아직 작성하지 마.
```

**확인:** 화면의 카메라 방향이 원하는 모습인지 확인하세요. AI가 좌표 비교를 통과했다고 보고하면 다음으로 넘어갑니다.

### 3-3. 촬영 위치와 코드 준비하기

**목표:** 전체 촬영 위치와 시험용 이웃 3장을 정하고 Playwright 촬영 코드를 준비합니다.

```text

```

**확인:** 전체 장수와 시험 타일 ID가 정해졌고, 시험 대상에 가로·세로 이웃이 모두 포함됐는지 AI의 결과를 확인합니다.

## 4. MFLUX로 화풍 바꾸기

**목표:** 촬영한 PNG를 원하는 화풍으로 편집하고, 이웃 3장의 형태·연결·처리 시간을 확인한 뒤 전체 타일을 변환합니다.

**결과물:** 768×768 시험·전체 편집 이미지, 사용한 설정과 처리 시간 기록

### 참가자가 할 일

원하는 화풍을 문장으로 정하고 아래 명령의 프롬프트에 넣습니다. 한 장 → 이웃 3장 순으로 실행해 형태·연결·처리 시간을 확인한 뒤 전체 처리 여부를 결정합니다.

3단계에서 촬영한 768×768 원본을 MFLUX에 그대로 넣습니다. 편집·보정·합성도 같은 해상도와 촬영 좌표를 사용합니다.

### 4-1. 준비한 모델과 편집 명령 확인

**목표:** 0단계에서 받은 모델을 사용할 수 있는지와 이미지 편집 명령의 옵션을 확인합니다.

0단계에서 받은 `.cache/model`을 그대로 사용합니다. 다운로드를 마치지 못했다면 `bash scripts/run.sh pnpm run setup:model`로 먼저 완료하세요.

```bash

```

실패하면 오류 전문을 AI에 전달하세요. 설치된 명령의 `--help`와 셋업 가이드를 기준으로 해결합니다.

### 4-2. 한 장 편집

**목표:** 내 맥에서 대표 PNG 한 장을 768×768로 편집해 원본의 지도 형태가 유지되는지 확인합니다.

`--prompt`의 문장을 원하는 화풍으로 바꿔 실행하세요. 영어가 어렵다면 AI에 문장 작성을 맡기세요. 입력은 3단계에서 촬영한 768×768 이미지 `captures/pilot.png`이며 원본은 보존합니다.

`--model .cache/model`은 미리 받은 모델의 위치이고, `--base-model flux2-klein-4b`는 그 모델의 종류를 지정합니다.

```bash
mkdir -p stylized/test-768

time bash scripts/run.sh uv run --locked mflux-generate-flux2-edit \
  --model .cache/model \
  --base-model flux2-klein-4b \
  --image-paths captures/pilot.png \
  --prompt "Restyle this city render as a warm hand-painted miniature city illustration. Preserve the camera, building footprints and heights, roads, waterways, and parks. Change the visual style while keeping the layout." \
  --steps 4 \
  --guidance 1 \
  --quantize 4 \
  --seed 42 \
  --width 768 \
  --height 768 \
  --output stylized/test-768/output.png
```

마지막에 표시되는 `time`의 전체 소요 시간에는 모델 로딩도 포함됩니다.

추가 학습이나 편집 LoRA는 사용하지 않습니다. `flux2-klein-4b`는 4스텝으로 편집하는 증류 모델입니다. 지시문만으로 형태 보존이 보장되지는 않습니다.

**완료 기준:** `stylized/test-768/output.png`가 768×768로 생깁니다. `captures/pilot.png`와 비교해 건물·도로·하천의 위치와 형태가 유지되는지 확인하세요.

### 4-3. 이웃 3장 편집하기

**목표:** 이웃 3장의 화풍과 연결 상태, 처리 시간을 확인합니다.

4-2의 한 장 편집 결과가 괜찮으면 진행하세요. **3단계에서 촬영한 이웃 3장만 편집**합니다. 결과를 확인한 뒤 4-4에서 전체를 촬영하고, 4-5에서 전체를 편집합니다.

**기본 처리 방식:** Python 프로그램을 한 번 실행해 모델을 메모리에 올리고, 같은 모델로 이미지 1 → 이미지 2 → 이미지 3을 차례로 편집합니다. 매 장마다 모델을 다시 로드하지 않습니다. 4-5의 전체 편집도 이 방식으로 진행하며, 프로그램을 새로 실행할 때 모델을 한 번 로드합니다.

별도 프로세스로 병렬 편집할 수도 있지만, 각 프로세스가 모델을 따로 로드하고 한 대의 맥북에서 GPU·메모리를 공유하므로 더 빨라지는지는 측정해야 합니다. `--image-paths`에 3장을 넣으면 참조 이미지 3장을 이용해 결과 한 장을 만드는 뜻입니다.

### AI 요청문 — 건물 기반 불빛 생성 코드 작성

### AI 요청문 — 선택한 서비스에 맞는 배포 준비

어떤 파일을 어디에 올릴지, 타일 URL·CORS를 어떻게 설정할지 정하고 배포 파일·명령을 준비하는 요청입니다. 로그인과 실제 배포는 참가자가 이어서 수행합니다.


### 참가자가 실행하고 확인

3. 웹페이지와 타일의 출처가 다르면 CORS를 설정합니다. 관리용 비밀 키를 브라우저에 넣지 않습니다.
4. 수정 파일이 갱신되도록 버전 경로나 캐시 무효화 방식을 정합니다.
5. 공개 주소에서 이동·확대·선택한 야경과 출처 표시를 확인합니다.
6. 모바일 공개라면 실제 폰에서 터치·고해상도·메모리·야경을 확인합니다.
